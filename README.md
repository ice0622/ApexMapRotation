# ApexMapRotation

Apex Legends の**ランクマップのローテーションを1日1回まとめて** Discord チャンネルに投稿する仕組み。
常時起動サーバーは使わず、GitHub Actions のスケジュール実行（バッチ）で完結するのでホスティングコストはゼロ。

## 仕組み

```
毎時実行
  → 覚えている「枠の終了時刻」を過ぎていなければ、何も変わりようがないので即終了
  → Apex Legends API を呼ぶ
  → ranked.current / ranked.next を「絶対時刻付きの枠」として取得
  → 覚えている並びを観測で検算する（ずれていれば自動で直す）
  → 並びで足りない枠を外挿し、当日 0:00〜24:00 を組む
  → 組んだ文面が前回投稿したものと違えば Discord へ投稿する
```

**API が1回で返すのは `current` と `next` の隣接1組だけ**です。1日分（4.5時間枠なら6〜7枠）を
出すには残りを計算で補う必要があり、そのためにマップの並びが要ります。

### 並びは自動で覚え、自動で直る

**人が触るものはありません。** 並びは Actions のキャッシュに覚えており、実行のたびに
観測で検算されます。

鍵になるのは**ランクのローテーションは順序が変わらず、マップの顔ぶれだけが入れ替わる**という
性質です。並び `[A, B, C]` を覚えているときに `A → D` を観測したら、**`A` の次にいた `B` が
`D` に置き換わった**と1回で分かります。集合を貯めて一巡待つ必要がありません。

```
警告: ローテーションが変わった可能性: Storm Point -> Broken Moon（World's Edge の次）。暫定で反映します
並び=[World's Edge -> Broken Moon -> E-District]（暫定）
投稿しました（6枠）。
```

この置き換えは「マップ数が変わっていない」ことを前提にした**仮説**なので、**暫定**として扱い、
次の観測で裏を取ります。裏が取れれば確定、外れれば観測を貯めて循環が閉じるのを待つ方式へ
落ちます（複数同時に入れ替わった・マップ数が変わった・順序が変わった場合）。

> ここで置き換えを試し続けてはいけません。マップが増えた場合に延々と入れ替えを繰り返し、
> 永久に収束しなくなります。暫定フラグはそれを防ぐためのものです。

並びを判別できないあいだは**外挿をやめ、API が保証する枠だけを投稿します**。
間違った1日分を出すより、短くても確実な分を出すほうがましだからです。

```
今日のランクマップ 9/14(月)
09:30-14:00 ブロークンムーン
14:00-18:30 ストームポイント
※新しいマップを確認中のため、ここまで
```

この状態でも枠が変わるたびに観測するので、数時間で自動的に確定します。

### コードの定数は種でしかない

[src/lib/rotation.ts](src/lib/rotation.ts) の `INITIAL_ROTATION` は、キャッシュが空のときの
出発点です。**これが古くても数時間の観測で正しい並びへ復帰する**ので、書き換える必要はありません。

```ts
export const INITIAL_ROTATION = ["World's Edge", 'Storm Point', 'E-District'];
```

マップ数は決め打ちしていません。3マップ前提の最適化を入れると、将来4マップになったときに
永久に判別できなくなるためです。

### 投稿するかどうかは文面の比較で決める

「組み立てた文面が前回投稿したものと違えば投稿する」という1つのルールで全部さばいています。

| 状況 | 文面 | 動き |
|---|---|---|
| 同じ日・同じ並び | 同一 | 投稿しない |
| 日付が変わった | 見出しが変わる | 投稿する |
| 顔ぶれが変わった | 中身が変わる | 投稿し直す |
| 判別中 → 判明 | 2枠からフルの表へ | 投稿し直す |

## ディレクトリ構成

```
src/
├── jobs/
│   └── postSchedule.ts     # 実行の入り口
└── lib/
    ├── apexApi.ts          # Apex Legends Status API クライアント（キー秘匿込み）
    ├── rotation.ts         # 並びの検算と更新・外挿・JSTの日境界
    ├── mockRotation.ts     # ダミーデータ
    ├── discord.ts          # Discord Webhook 送信
    ├── memory.ts           # 実行をまたいで覚えること（Actions のキャッシュに置く）
    └── messages.ts         # 通知の文面（見た目を変えるならここ）
tsconfig.json               # 型チェック用（ビルドには使わない）
.github/workflows/
```

TypeScript で書かれていますが**ビルドはありません**。Node 24 が `.ts` をそのまま実行します
（ネイティブ type stripping）。`tsc` は型チェック専用です（`npm run typecheck`）。

**リポジトリに書き込むものはありません。** 永続データを持たないので、bot による
自動コミットは一切発生せず、ワークフローの権限も `contents: read` だけです。

## 通知メッセージ

```
今日のランクマップ 9/14(月)
22:00-02:30 ワールズエッジ
02:30-07:00 ストームポイント
07:00-11:30 Eディストリクト
11:30-16:00 ワールズエッジ
16:00-20:30 ストームポイント
20:30-01:00 Eディストリクト
```

- 0時をまたぐ枠は**切り詰めません**。最初と最後の枠は前後の日にはみ出していますが、時刻はそのまま出します。
- 将来 X(Twitter) にそのまま流せるように、**マークダウンを使わず**マップ名は**日本語のみ**にしています。英名併記にすると X の 280 カウントを超えるためです。
- 280 を超える場合（枠が3時間以下に短くなったシーズンなど）は、終了時刻を省いた短縮形へ自動で切り替わります。

文面はすべて [src/lib/messages.ts](src/lib/messages.ts) に集約しています。
見出しや区切り記号は `TEXT` 定数を、日本語マップ名は `JP_MAP_NAMES` を編集してください。

## セットアップ

1. **Discord Webhook を作成**
   対象チャンネル → 連携 → Webhook → 新しいWebhook → URLをコピー。
   ※ Webhook URL は知っている人が誰でも投稿できるため、秘密として扱ってください。

2. **GitHub のシークレットを登録**
   リポジトリの **Settings → Secrets and variables → Actions** に登録：

   | シークレット名 | 内容 |
   |---|---|
   | `DISCORD_WEBHOOK_URL` | 通知先チャンネルの Webhook URL |
   | `APEX_API_KEY` | Apex Legends Status の APIキー（後から追加でOK） |

   `APEX_API_KEY` を登録するまでは自動でモックモードになります。

3. **Actions を有効化**
   Actions タブでワークフローを有効化すれば、毎日 JST 0:00 の投稿が動き始めます。

## 実行スケジュール

cron は `0 * * * *`（毎時）の1本です。

**API 呼び出しは1日6〜7回です。** 観測した枠の終了時刻を覚えているので、それを過ぎるまでは
キャッシュを読むだけで終わります。結果、API を叩くのは「枠が変わるたび＋日付が変わるとき」だけです。

毎時にしている理由は2つです。

- **取りこぼしへの備え**。GitHub の schedule は宣言どおりに実行されません。このリポジトリの
  実測では `*/5 * * * *`（本来1日288回）が **約3時間に1回まで間引かれていました**（8日間で60回＝3%）。
  毎時にしておけば 0:00 の回が落ちても次の時間で取り返せます。
- **ローテーション変更への追従**。枠が変わったことに気づくには、枠長（4.5時間）より
  細かい間隔で見に行く必要があります。

覚えていること（並び・最後に投稿した文面・次に確認する時刻）は `actions/cache` に置いています。
コミットしないのは、毎日変わる値なので履歴が膨らむ一方、**失っても数時間の観測で学習し直す**からです。
キャッシュは7日アクセスが無いと消えますが、毎時読むので実質消えません。

## 手動実行

Actions タブ → **Post Apex ranked map schedule** → **Run workflow**

- `force: true` — 前回と同じ内容でも投稿し直す
- `use_mock: true` — APIキー無しでもダミーデータで Discord 送信を確認できる
- `dry_run: true` — 送信せず、文面と文字数をログにだけ出す

```bash
gh workflow run post-schedule.yml -f dry_run=true
```

## ローカル開発

**Node 24 以上が必要です**（`.ts` の直接実行のため）。実行だけなら `npm install` は不要です。

```bash
cp .env.example .env
# .env の DISCORD_WEBHOOK_URL に本物の Webhook を入れると実際に投稿が届く

npm run post:dry      # 送信せず文面と文字数だけ出す（フォーマット調整用）
npm run post:mock     # ダミーデータで実際に Discord へ送る
npm run post          # 通常実行

npm ci                # 型チェックを使う場合のみ（typescript を入れる）
npm run typecheck     # 型チェック（CI でも push 時に自動実行）
```

- 枠が短いシーズンの短縮形: `MOCK_SLOT_MINUTES=180 npm run post:dry`
- ローテーションが変わった日の動き: `MOCK_POOL="World's Edge,Broken Moon,E-District" npm run post`
  （`MOCK_POOL` はモック側の並びだけを差し替えるので、覚えている並びと食い違う状態を作れます）

> 覚えていることはローカルでは `.cache/`（gitignore 済み）に出ます。
> 状態をまっさらに戻すには `rm -rf .cache` してください。

## モックモード

`APEX_API_KEY` が未設定、または `USE_MOCK=true` のときは実APIを呼ばずダミーデータを使います。
前日22時を起点に4.5時間の枠を並べ、実行時刻を含む枠を `current` とするので、本番と同じ形の
スケジュールが1日分出ます。並びは `INITIAL_ROTATION` を使います（`MOCK_POOL` で上書き可）。

## 依存関係とサプライチェーン対策

- **実行時依存はゼロ**です。本番（Actions の cron）は `npm install` 自体を行わず、Node 24 が `.ts` を直接実行します。
- devDependencies は `typescript` と `@types/node` の2つだけ（型チェック専用・バージョン完全固定・どちらも install スクリプトなし）。
- [.npmrc](.npmrc) で `ignore-scripts=true`（install スクリプトの自動実行を禁止）と `save-exact=true` を設定済み。
- ワークフローの権限は `contents: read` のみです。

## 注意点

- Apex Legends API は非公式サービスで公式のSLAはありません。取得に失敗したときは投稿せずスキップし、次の時間の実行で再試行します。
- Discord への送信に失敗した場合は「最後に投稿した文面」を進めないので、次の時間の実行で再送されます。
- **実測できるのは `current` と `next` の2枠だけで、それ以降は外挿です。** 並びを判別できないあいだは外挿せず確定分だけを出し、確定したら自動で出し直します。
- **枠の格子は毎日ずれます。** 4.5時間×6＝27時間なので境界は1日3時間ずつ後ろへ動き、1日の枠数も6と7を行き来します。格子は決め打ちせず API の絶対時刻をそのまま使うため、これは自動的に追従します。
- **既知の限界**: ローテーションが変わった日の訂正投稿では、新しい並びを1日全体に遡って適用するため、その日の**すでに終わった枠の表示が実際と食い違います**（例: 朝に E-District だった枠が Broken Moon と表示される）。訂正した時点より後の枠は正しく、0:00 の投稿もチャンネルに残っています。発生はシーズンに1回で、行動に使う情報ではないため直していません。
- 枠の長さは API の実測値（`start` / `end`）をそのまま使うため、定数で持つ必要はありません。
- リポジトリに **60日間** 活動が無いとスケジュールは自動停止します（GitHub仕様）。手動実行や任意のコミットで復帰します。
